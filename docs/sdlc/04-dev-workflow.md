## Development Workflow — Story Lifecycle

One story, start to finish, as it actually runs on this repo today. Stages marked
**GAP** do not exist — the tooling is absent, not merely unused. Stages marked
**From Sprint 1** are agreed future practice and are **not in force today**: GitLab
issues exist and carry zero work, there is no `.gitlab/` templates directory, no
sprint has been run, and production is not deployed. Do not write an MR description
claiming you ran any of them.

This section owns the **sequence**: what happens, in what order, who does it, and
what has to be true before the next stage starts. It does not own the mechanisms it
depends on. Where a topic has a single owner elsewhere, this section states only the
consequence it depends on and links.

### After you click Merge

Nobody was watching this seam, so it is named here. **The maintainer who merges owns the `main` pipeline until `deploy:qa` reports success** — nothing alerts anyone if it does not (`08-monitoring.md`: Uptime Kuma is planned, not installed), `main` has already moved, and QA keeps serving the previous digest while everyone assumes the change is live. In practice that is a five-to-ten minute wait on the pipeline page after clicking Merge; if the merger must leave, they hand the pipeline to a named person in the MR thread before they do. A failed `publish` or `deploy:qa` is not the author's problem to discover at stage 17.

### QA reflects the last merge, not your story

`deploy:qa` runs on **every** green pipeline on `main` and recreates the container. There is no `resource_group: qa` today (`06-cicd.md` §4.4 owns that fix), so developer A's merge can delete the container developer B is verifying against, mid-story, with no warning and no notification. Two consequences for this workflow:

1. **Before stage 17, check that the digest on QA is the one your merge produced** — the same `docker inspect --format='{{.Image}}'` comparison `deploy:qa` makes. If it is not, your story was verified on someone else's bytes, and the verification is void.
2. **Verification is sequenced against merges, not against the clock.** If two stories merge within the same hour, the second merger says so in the first MR's thread.

### When a merged story fails QA verification

This is the most likely event in a process where verification is post-merge by design, and it had no defined path. It does now.

1. **The non-author verifier (stage 17) raises it in the MR thread of the merged MR**, with what they did and what they saw. Not chat, not verbally — the thread is the record and it survives the squash.
2. **The merging maintainer decides revert or fix-forward, and writes the reason in that thread.** Default is **fix-forward**: a new branch through stages 3–15. Revert (`git revert` on a branch, then a normal MR — recipe in `03-git.md`) is for a change that is actively producing wrong output on QA and cannot be corrected the same day.
3. **A migration changes the answer.** Rolling the image back does not roll the schema back, and the restore procedure — including the forensic copy first and the reference-number hazard afterwards — is `07-deployment.md`'s. Do not improvise it from this section.
4. **From Sprint 1:** the issue reopens rather than a new one being cut, so the story's history stays in one place, and it stays in the current milestone rather than counting as delivered. Today, the MR thread is that record.
5. **The desk is told by the person who validated the story at stage 2**, on the same day, in the words the desk used at stage 1 — "the number on the printed quotation is still wrong; do not send one for X until you hear from me."

### The production stage, when it exists

Production is **not deployed**, and this section does not own the reason, the preconditions or the sequence. In order:

- **Hardware and the rest of the blockers:** `07-deployment.md`. Summarised in one line so nobody plans around it: production is blocked on a RAM upgrade to a shared Windows laptop (192.168.1.37, i3-1115G4, 2 cores, 8 GB with ~491 MB free) already running Pickup Ops (:3000), Newtech Inventory (:8000), IIS (:8080) and AnyDesk (:7070). - **The port:** production is `18080` on 192.168.1.37 (the plan reserves 18080–18099 for new production apps). It must **not** claim 8081: that is QA's port on .40, and on .37 8080 is IIS and 8081 is unverified. Recorded in `07-deployment.md`'s environment table.
- **The one thing this section asserts about production:** it **pulls the digest QA tested and never rebuilds**. Any job graph in which `build` runs on a `v*` tag destroys the guarantee the whole pipeline exists to provide (stage 16).

### Every rule in this section, and what enforces it

A rule marked mandatory with no mechanism teaches readers that the mandatory list is optional. So, honestly:

| Rule | Status | Mechanism |
|---|---|---|
| No push to `main` | **MANDATORY** | `push_access_level=0`, verified on the instance (`10-roles.md` §2) |
| Pipeline green before merge | **MANDATORY** | `only_allow_merge_if_pipeline_succeeds=true` |
| All discussions resolved before merge | **MANDATORY for a Developer author** | `only_allow_merge_if_all_discussions_are_resolved=true`. A Maintainer author can resolve their own threads — convention only |
| A Developer does not merge their own work | **MANDATORY** | `merge_access_level=40` |
| A Maintainer does not merge their own MR | **RECOMMENDED until it has an owner** | Nothing in Free prevents it. Detective control: `10-roles.md` §2's monthly API sweep flagging `author.username == merge_user.username`. It needs a named owner and a date, or it stays a recommendation |
| `npm run build && npm run typecheck && npm test` before push | **MANDATORY** | Machine-checked downstream: the same suite runs in CI and blocks the merge. Locally it only saves you the round trip |
| A skip in CI is a failure | **MANDATORY in intent, no machine check yet** | `06-cicd.md`'s `test:no-skips` job (reads the JUnit XML, fails when the artifact is missing) is the mechanism and is **not built**. Until it lands, the *reviewer* opens the `test` job log. An author-declared skip count is not a measurement and should not be asked for |
| "My machine tested Word; CI tested LibreOffice" in the MR | **RECOMMENDED today; MANDATORY once the MR template exists** | No automated check is possible — CI cannot know what ran on a laptop. It becomes a checkbox in `.gitlab/merge_request_templates/` (`01-agile.md`), enforced by the reviewer opening a thread when it is missing. Today: the reviewer asks |
| A behaviour change ships its tests in the same MR | **RECOMMENDED — checkable, unowned** | Proposed to `06-cicd.md`: a job comparing `git diff --name-only origin/main...HEAD` and warning when `server/src/**` or `shared/**` moved without any `*.test.ts`. It has false positives (a comment-only change), so it warns and the reviewer dismisses it in a thread |
| Guard self-checks are never weakened to go green | **MANDATORY, review-enforced** | No machine check exists — a weakened assertion is still a passing test. The reviewer refuses the MR. This is the single most important thing a reviewer of this repo does |
| MR quotes an issue number | **From Sprint 1 — not in force today** | GitLab issues are unused; there is nothing to quote |
| The stage-4 design answers are written before coding | **From Sprint 1 in the issue; RECOMMENDED today in the MR** | The reviewer asks for them at stage 13 |
| Never hot-fix the QA container by hand | **RECOMMENDED — nothing can enforce it** | QA has no authentication (`09-security.md` §0), so no technical control exists short of closing TODO-SEC-01. Partial detective control: the next `deploy:qa` re-asserts the digest and silently reverts the edit, which is how you find out |
| The merging maintainer watches the pipeline to `deploy:qa` | **RECOMMENDED — no alerting exists** | Nothing notifies anyone of a failed `publish` or `deploy:qa` (`08-monitoring.md`). It becomes checkable when Uptime Kuma or a pipeline notification lands |
| The squash message carries the why | **RECOMMENDED (0 of 5 compliance)** | `03-git.md` records that every MR-merged commit has an empty body. The MR description is the canonical record instead; a scheduled `git log --format='%H%n%b'` warning is possible if anyone wants the rule back with teeth |
| Money stays integer paise | **MANDATORY, mechanically checkable once lint lands** | `06-cicd.md` §4.1's scoped `no-restricted-syntax` rule, which passes clean on today's tree. Until then: the reviewer, using the scoped wording at stage 6 — not the blanket "never divide by 100", which the code correctly violates six times |

Nobody owns `.gitlab-ci.yml`, and five sections propose edits to it, several of them mutually exclusive. Nothing in this section may be implemented by editing that file directly: `02-ai-rules.md` puts it behind a human gate, and the sequencing of CI changes belongs to `06-cicd.md` and the SysAdmin hat in `10-roles.md`.
